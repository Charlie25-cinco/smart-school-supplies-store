# Prototype requirements and traceability

This document applies ISO/IEC/IEEE 29148 conventions: uniquely identified, unambiguous and verifiable requirements; rationale/source/priority/acceptance criteria; stakeholder/system/design separation; and implementation/test traceability. It does not claim full compliance. Formal stakeholder signatures, lifecycle baselines, exhaustive non-functional measurement, and independent validation are simplified for the student prototype.

Baseline: user-approved catalog + local POS/IMS scope, amended by SQLite approval and acceptance of manual standalone LAN operation on 2026-10-10. Sources: `Plan.docx`; conversation decisions; AI Engineering Standard v1.3.0. Automatic startup is deferred by explicit user instruction. Requirements are not a claim that every business-plan aspiration is implemented.

This amendment extends REQ-002–004 and SR-002–003. Paid receipts contain item subtotal plus any delivery fee; all money remains integer centavos. Stock total denotes units not yet deducted by paid completion; it can include reserved goods out for COD delivery. Available stock excludes those reservations. It is not a physical shelf count during dispatched unpaid orders.

## Design constraints

| ID | Description | Rationale | Source | Priority | Acceptance criteria |
|---|---|---|---|---|---|
| DC-001 | The POS shall use Laravel, Blade, and one SQLite database local to the server computer. | Match programmer preference while sharing records through the store LAN. | Framework/SQLite approval; accepted LAN plan | High | Laravel uses PDO SQLite without MySQL; device browsers call Laravel and never access the database as a network-shared file. |
| DC-002 | The public catalog shall be standalone static files, prepared for future Cloudflare Pages deployment. | Separate public hosting from private local operations. | User hosting decisions | High | Catalog can be served from its own directory with relative assets/JSON; no PHP/database required; no deployment performed during this milestone. |
| DC-003 | Catalog availability and service details shall be confirmed manually by staff. | Local inventory is not publicly synchronized. | Approved architecture tradeoff | High | Catalog explicitly says availability is confirmed; staff select Messenger channel for confirmed sales; no public live-stock claim. |
| DC-004 | The public catalog shall remain prepared for Cloudflare Pages while POS records remain on the store host. | Preserve the agreed public/private architecture. | Accepted revised plan | High | Document root catalog and output directory dot; no Laravel hosting, account connection, publication, or automatic catalog synchronization introduced. |

Out of scope: customer accounts, public online order database/tracking, automatic Messenger sending, bots, payment gateways, printer control, cloud/local stock synchronization, expense/profit accounting, paid-sale returns/refunds/voids, and multi-branch operation. Local staff order tracking and unpaid cancellations are included by the 0.4.0 amendment. Revisit remaining features through a new approved plan.
